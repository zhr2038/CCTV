# 然然家庭录像助手 V2：可信、可找、值得回看

## 1. 产品结论

当前产品把“模型处理完成”误当成“生活事实已经量准”。这两个概念必须拆开。

V2 不再以活动时长仪表盘为首页，而围绕三个家庭任务设计：

1. **找得到**：用自然语言快速找到某个真实片段。
2. **值得回看**：自动整理当天高光、成长片段和可播放的短视频。
3. **看得懂但不装精确**：只在观测条件足够时统计；其余明确写成“监控确认”“至少”“约”“可能漏拍”或“未知”。

模型覆盖率、关键帧数、GPU 队列等内容移入“系统状态”，不再占据家庭首页。

## 2. 已确认的失真来源

### 2.1 喂奶时长是人为扩窗，不是测量值

`activity_inference.py` 会把一个 Qwen3 喂奶证据点扩成前后各 120 秒。2026-07-31 的 5 个喂奶会话因此显示为 24 分钟，其中 4 个会话都只有一个证据点。这个数字不能称作“可见至少时长”。

V2 规则：

- 单个或稀疏证据只能计为“监控确认 1 次”，不显示时长。
- 只有连续录像中识别到开始和结束，且中间覆盖完整，才显示区间时长。
- 跨摄像头在 20 分钟内的重复证据可以合并，但不能用固定窗口补齐时长。

### 2.2 睡眠时长是采样推定，不是逐秒测量

床头录像每 10 分钟选择一个睡眠候选，确认后把该锚点前后各 5 分钟计入睡眠，再合并成会话。2026-07-31 的约 8.3 小时来自 50 个正向锚点的覆盖，并非逐秒确认。

V2 规则：

- 展示为“推定睡眠窗口”，附边界误差和录像覆盖率。
- 缺失录像必须切断区间并标成未知，不能跨越缺口补齐。
- Qwen3 重点复核入睡、醒来和中间异常状态变化，不承担每帧分类。

### 2.3 动作摄像头不能产生全天总时长

客厅、厨房和宝宝房顶部是动作触发片段。没有片段只代表没有被摄像头触发，不能代表活动没有发生。因此玩耍、爬行和坐姿在这些摄像头上只能提供“出现过的片段/会话”，不能提供全天总时长。

### 2.4 搜索会把所有候选硬过滤成零结果

实测在 2026-07-31 搜索“宝宝喝奶”耗时 14.05 秒，返回 0 条；同一天数据库里已有 5 个喂奶事件。当前流程只验证单张召回图，并把 Qwen3 判为不确定的结果全部丢弃。

V2 搜索必须分层返回：

- **已确认匹配**：时序片段明确满足查询。
- **可能相关**：向量相似，但模型未能确认。
- **事件记录**：数据库里已有的结构化事件。

任何一层都不能静默吞掉其余候选。搜索默认全库，日期和摄像头作为可选筛选；已选择的日记日期不应暗中限制搜索范围。

### 2.5 “处理覆盖率”与“生活可观察率”混在一起

文件分析 100% 只代表已处理稳定文件，不代表当天生活被完整观察。2026-07-31 床头连续录像覆盖约 88.05%；三路动作触发摄像头无法计算全天负向证据。

V2 同时展示三种独立状态：

- **数据新鲜度**：最新录像处理到几点。
- **录像覆盖率**：连续摄像头实际覆盖了当天多少时间。
- **结论可信度**：该指标能否计数、估时或只能作为目击片段。

## 3. 新的信息架构

### 今日

- 顶部固定搜索框：“找喝奶、红衣服、玩积木、第一次坐起来……”
- 数据状态一句话：“处理到 09:32；床头录像覆盖 88%；动作摄像头可能漏拍。”
- 今天发生了什么：按时间排序的证据卡片，卡片内直接播放，不再使用远离时间轴的巨大独立视频窗。
- 今日三个可信摘要：喂奶确认次数、推定睡眠窗口、值得回看的片段数。不可测的字段显示“未知”，不显示 0。
- 值得确认：每天最多 3 条真正会改变统计或纪念集的候选。

### 搜索

- 默认搜索全部录像，可选日期、房间、活动和“只看已确认”。
- 先在 1 秒内展示向量召回和已有事件，再异步更新 Qwen3 验证徽标。
- 查询扩展：喝奶同时召回奶瓶、奶嘴接触、成人喂食等语义；动作查询使用短视频时序，而不是只看单帧。
- 零高置信结果时仍显示“可能相关”，并解释为什么未确认。

### 回忆

- 每日 5–10 个高质量片段自动组成“然然今天”。
- 周/月日历按有价值片段密度浏览，而不是按模型观察数浏览。
- 一键导出原片片段或家庭相册式短视频；原录像保持只读。

### 规律

- 只展示通过质量门槛的周趋势。
- 喂奶：监控确认次数和时间点分布，不推断奶量。
- 睡眠：推定窗口、录像覆盖率、边界误差。
- 玩耍/爬/坐：动作摄像头显示会话或目击次数；只有连续覆盖时才给可见时长下限。

### 系统

- 摄像头最后写入时间、缺片、坏文件、处理队列、GPU 和模型覆盖率。
- 家庭首页不再展示 230 万观察、Qwen3 覆盖率等工程指标。

## 4. 可信数据契约

V2 首期不需要修改 SQLite 表结构，可以在 API 聚合层派生以下字段并保持旧事件兼容：

```json
{
  "measurement_mode": "sighting_only",
  "status": "confirmed_on_camera",
  "count": 5,
  "duration_seconds": null,
  "lower_bound_seconds": null,
  "upper_bound_seconds": null,
  "boundary_error_seconds": null,
  "recording_coverage": 0.8805,
  "support_count": 6,
  "negative_evidence_valid": false,
  "notice": "监控确认 5 次；动作触发录像可能漏拍，不能作为全天实际总数"
}
```

`measurement_mode` 仅允许：

- `exact_interval`：连续证据明确覆盖开始和结束。
- `bounded_interval`：可报告大致区间和边界误差。
- `visible_lower_bound`：只能报告明确可见的下限。
- `sighting_only`：只能计目击会话，不能报时长。
- `unavailable`：当前录像无法支持该指标。

页面不得把 `null` 转成 0。

## 5. 处理架构调整

### 单一入库账本

媒体探测只能有一个权威入口。每个文件稳定后，按摄像头配置一次性创建视觉、音频、水印等任务。视觉流程不得用 `audio_enabled=False` 把文件提前标为已探测，否则会造成音频任务漏建。

### 新数据快车道

- 每 5 分钟发现新文件。
- 连续两次大小不变且距最后写入 10–15 分钟后进入任务队列。
- 最近 48 小时始终高优先级；历史回填使用低优先级并可暂停。
- 活动聚合只在对应文件的视觉任务完成后增量更新，不重跑整月。

### 事件理解

```text
原始片段 -> 轻量召回 -> 原片短时序复核 -> 原子观察
原子观察 -> 跨摄像头去重/连续状态分段 -> 生活会话
生活会话 + 覆盖率 + 测量模式 -> 可展示指标
```

## 6. 人工工作量

不再要求逐条复核。默认每天最多 3 条，只选择以下情况：

- 会让喂奶次数发生变化的边界候选。
- 会改变睡眠开始/结束超过 10 分钟的候选。
- 可能进入成长纪念集的候选。

其余机器结果保留为机器状态，不强迫清空。人工结论用于校准，不作为每天使用产品的前置条件。

## 7. 验收门槛

1. 2026-07-31 喂奶卡片显示“监控确认 5 次”，不再显示 24 分钟。
2. 搜索“宝宝喝奶”能返回当天已有的喂奶事件；即使 VLM 未确认，也必须显示可能相关候选。
3. 搜索初步结果 1 秒内出现，深度验证异步更新；不让用户空等 14 秒后看到 0 条。
4. 播放按钮点击后 100 毫秒内出现加载状态，成功后在当前卡片内播放，失败时给出可重试原因。
5. 动作触发摄像头没有事件时显示“未知/未观察到”，不得显示“0 次”。
6. 睡眠显示窗口、覆盖率和边界误差；录像覆盖低于 80% 时不发布全天总时长。
7. 新稳定录像在正常开机情况下 20 分钟内出现在今日页。
8. 每日人工复核不超过 3 条；不复核也能正常使用搜索、回看和已确认事件。

## 8. 实施顺序

### 第一阶段：先恢复可信度

- 删除所有由固定扩窗产生的“活动时长”展示。
- 加入测量模式、未知状态、录像覆盖和结论说明。
- 搜索改为分层结果并默认全库。
- 修复播放状态反馈和就地播放。
- 修复媒体探测造成的音频任务漏建。

### 第二阶段：让它每天有用

- 今日片段流、自动高光和“然然今天”。
- 最近 48 小时增量快车道。
- 系统指标移入独立状态页。

### 第三阶段：再做可靠规律

- 连续摄像头状态分段和睡眠边界复核。
- 喂奶时序召回率评估与跨摄像头去重。
- 用少量高信息样本计算精确率、召回率和边界误差；未达到门槛的指标继续保持“监控目击”口径。

## 9. 2026-08-01 已落地的第一批改动

- 页面不再把固定扩窗显示成喂奶、玩耍、爬行或坐姿的真实时长；零命中改成“未发现”，并明确不等于 0 次。
- 睡眠只有在床头录像覆盖达到 80% 时才显示约时长；低覆盖时只显示“有睡眠候选”。
- “宝宝喝奶”等已知活动查询先查结构化事件，不再让向量模型把已有结果过滤为 0。全库实测从原来的 14.05 秒、0 条，改为 0.132 秒、10 条已有事件。
- 任意开放式查询保留“可能相关”结果，不再硬过滤为空。当前轻量索引冷启动约 19.6 秒，热搜索约 4.0 秒；后续应换成常驻 ANN 索引，把热搜索压到 1 秒内。
- 在线搜索改用 CPU 上的轻量查询编码器，避免与正在占用约 31.5 GB 显存的 Qwen3 批处理争抢 RTX 5090。
- 视觉探测不再用 `audio_enabled=False` 提前结束媒体入库；每轮会自动补建已探测文件缺失的音频任务。
- 音频 worker 的配置已扩展到客厅、宝宝房顶部、厨房和宝宝床头四路摄像头。
- 搜索结果会自动定位到时间轴与播放器；修复了桌面端 sticky 证据图覆盖播放按钮的问题。真实浏览器复测中，点击会立刻显示生成反馈并在约 4 秒内开始播放。
- 全部 99 项自动化测试通过；局域网服务健康检查返回 `ok`，源录像保持只读。
